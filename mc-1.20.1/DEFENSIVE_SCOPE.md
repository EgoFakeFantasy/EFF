# 防御开发范围与验证边界

EFF 的完整性校验、外部监督、进程隔离、可信重启、异常检测和自动化防御测试可以分别推进。
这些工作不以 Daybreak 或额外的网络安全计划准入为前提。某项工具操作若被环境审批阻止，
应记录具体命令、原因与替代路径，不把整个防御项目归为无法开展。

| 能力 | 工程实现与验证 | 不应推导出的结论 |
| --- | --- | --- |
| 启动完整性 | 固定 JDK、agent、bootstrap、native companion；独立复制、哈希与严格参数准入 | 同权限任意原生代码无法修改内存 |
| 外部监督 | 独立进程观察 PID/创建时间、窗口、心跳与控制器故障；保留原始失败记录 | JVM 内任意自报数据都可信 |
| 隔离 | 已有受限宿主与控制通道，限制游戏对外部控制面影响 | 与目标同 JVM 的两个模组已互相隔离 |
| 可信重启 | 从审核并封存的输入创建后继实例，独立验收重启与状态恢复 | 原窗口或原实体连续存活 |
| 写前防护 | 针对受管对象的已审查字段、容器引用与固定 JVM 包装入口，在写入前拒绝 | 所有 JNI、VarHandle、直接原生内存写都已覆盖 |
| 连续存活实战 | 同 JVM、原对象、原 id/UUID 登记、真实存储血量、原 PID/HWND、目标关联攻击与录像 | 一次有界测试证明对手所有路径或任意内核攻击无效 |

当前确认的工程边界包括：后置独立 native ClassFileLoadHook 的负例、直接 native 内存写、
未经审查的内部 Unsafe 入口，以及信任根本身在同权限进程内被改写的可能性。普通用户态
守护不能承诺超过 Windows 内核的保护，也不能靠“换成 C/Rust 实现”建立新的权限边界。
这些属于能力与证据限制，不能成为停止已可实现的防御工作的理由。

当前 pig2 和永爱的实战通过均已撤回：前者损失了场景实体，后者缺少可核对的正常可见攻击。
旧单目标探针不能验收全部 EFF 场景角色。新判定要求完整的攻击前实体清单、逐项双端连续存活
和可见攻击证据；Java 侧完整场景采样与实际客户端攻击链路尚待接入，不宣称已经修复防御。

实战须保持原始对手样本、不按模组名字特判防护、不重新插入原实体、不用健康缓存掩盖损坏。
对手名字仅用于明确启用的测试场景与攻击来源归因。没有目标关联破坏操作证据时，调用进入或
返回都不能算已完成有效交战。诊断计数也不能替代严格攻击回执。

录像响应超时会立即锁存失败，并与窗口消失分开记录；仅在原进程/窗口身份仍一致时，额外保留
最多3秒失败后诊断录像。晚到数据单列，恢复不能清除失败。文件解码成功与交战验收成功也分开。
本轮没有清理用户文件、重建虚拟机或修改系统杀软设置。

为定位响应超时，测试诊断可只观察本轮明确绑定的服务端/渲染线程：最多60次、24层栈，按3秒
采样调度预算运行，独立文件记录，不修改对象且不进入验收判据。ThreadMXBean调用本身若被
JVM阻塞，用户态不能保证强行在3秒中断；因此必须保留采样自身耗时与实际总耗时。诊断依赖
提前在独立线程初始化，未就绪或权限失败只记诊断不可用，不能延迟或放宽实战验收。

具体构建与实测结果见 [录像验收记录](../mc-forge-1.20.1/RELEASE_0.8.0.md)；候选离线通过不等于
原版永爱或 pig2 在该候选上已通过。
