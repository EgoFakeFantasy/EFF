# 1.20.1 多 JVM 托管研究场（0.3）

这个入口将原来的同 JVM 对象重建扩展为真实进程替换。默认普通模组安装仍使用原有研究场；**必须通过 `start-managed.ps1` 启动，才能替换 MC 本身**。这轮仅适配 Java 版 1.20.1，26.3 版没有接入此控制器。

## 运行边界

```text
Node 外部控制器（可信根，拥有已提交状态和当前进程资格）
 ├─ 判定 JVM：独立计算干预，复核执行 JVM 的候选结果
 ├─ 执行 JVM：运行有边界的研究场语义，计算实体/事件/授权的下一状态
 └─ MC JVM：客户端 + 集成服务端；把已提交状态落实为原生实体、牵引、冻结、出口
      └─ 既有 Node 剧情桥：本地 Ollama 推理、原文与界面状态
```

三个 JVM 是不同 OS 进程。`rebuild instance.world` 仍表示场景对象重建；新增的三种 `runtime.*` 干预才会结束并启动对应 JVM。模型推理仍由既有剧情桥调用本机 Ollama，权重没有移进 Java。判定和执行使用同一份受限语义的独立求值，两者隔离进程故障，不构成两种独立算法对共同逻辑错误的证明。

## 启动

需要 Java 17 JDK、Node.js 22+，首次 Gradle/Fabric 依赖准备需要网络。Ollama 可选；已安装的 `qwen3.5:4b` 会由研究场试玩入口启用，失败明确标为规则回退。

```powershell
.\start-managed.ps1 -Jdk 'C:\path\to\jdk-17'
# 指定独立的数据目录；不要指向自己的 MC 世界文件夹
.\start-managed.ps1 -Jdk 'C:\path\to\jdk-17' -Directory 'C:\path\to\eff-managed'
# 可选：判定进程使用另一个兼容 Java 17 字节码的 JDK；MC 仍为 Java 17
.\start-managed.ps1 -Jdk 'C:\path\to\jdk-17' -PolicyJdk 'C:\path\to\jdk-25'
```

启动会导出本机私有启动清单，再由 Node 直接持有 MC 子进程，不套一层会残留 MC 的 Gradle 重启命令。Java 参数文件避免 Windows 命令行长度上限。不要分享 `private-launch.json`、进程参数文件、研究场状态或日志。Ctrl+C 关闭控制器及它持有的子进程；MC 主菜单正常退出会发送 goodbye，控制器不会将其当崩溃反复拉起。

托管启动的 MC 进程专供研究场；不要在这个进程加载需要保留的普通世界。同一数据目录只允许一个控制器。控制器自身异常退出后会保留锁；先核实旧控制器确已退出，再移除该目录中的 `authority/controller.lock`。不要在进程仍在运行时删锁。新建数据目录开始新战局，原目录可接续战果。

## 玩家与 AI 的干预

原有组合、条件断言和一次性触发器保留，每次最多三次修改。例如：

```text
erase entity.avatar
# 如果只移除身体，外来者仍可根据实测结果恢复

disable control.tether; disable event.possess; disable authority.recovery
# 撤销是在控制器提交的，换 JVM 不会重置它

rebuild runtime.execution
rebuild runtime.policy
rebuild runtime.host
# 第三个会真的关闭 MC 窗口并重新启动，再进入重新生成的专用研究场

erase entity.avatar; refuse ending.owned
```

外来者恢复/替换指令同样经过判定。撤销 `authority.recovery` 后，外来者不能靠旧检查点、实例重建或 JVM 重建获得恢复授权。系统在故障后自动启动新进程，是基础设施恢复，不会替外来者恢复已经失去的游戏权限。AI 读取实际执行回执和运行层信息；只有出现相应进程故障记录时，才向外来者开放运行层替换建议。玩家的编辑草稿不会进入外来者上下文。

## 提交、恢复与失效隔离

1. 外部控制器串行处理带当前版本的请求。执行 JVM 计算候选，判定 JVM 独立复核；不一致时不提交。
2. 控制器把完整逻辑状态写到临时文件、同步文件内容后替换 `committed.json`；提交失败不允许原生应用。状态包含权限、检查点内容/归属、封印、触发器及已触发标记、轮次和结局。校验失败停止启动，不默默重置成新战局。
3. MC 应用已提交状态。`projectionPending` 表示原生投影尚未对齐；它不是“画面已恢复”的证明。MC 在应用前失效，新宿主再次应用同一提交。
4. 每个工作进程使用代次和请求身份；替换前先撤销旧身份，迟到 stdout 无法完成新请求。MC 请求另带随机租约、会话和宿主代次；换宿主先换租约、确认旧进程结束，再启动新进程。旧宿主的排队写入也被拒绝。
5. 工作进程无进展时有时限、至多一次事务重试和重启窗口熔断。MC 检查真实客户端 tick 与服务端循环进展，不把世界冻结或实体不动当死机；原版暂停允许服务端暂停。启动另有宽限时间。MC 连续故障会熔断，保留战果供诊断。

检查点改为控制器单次提交中的数据，和权限一起落盘；不再从被结束的 MC JVM 的堆或临时副本中恢复。MC 重新启动后使用新建的、按会话和宿主代次命名的专用世界，依照已提交战局重新生成实体与地图。**这里恢复的是研究场的战局，不是任意 MC 世界的完整内存、第三方模组状态或背包快照。** 普通世界没有接入这种自动重启。

## 防护范围

这能隔离单个可替换 JVM 的退出、假死、进程内状态丢失，以及旧代次回复。工作进程不加载 MC/第三方模组，不执行模型生成的 Java 或系统命令，禁用运行期 attach，清除 JVM 环境参数注入入口，限定内存。所有结束操作只作用于控制器自己持有的子进程。

Node 控制器、其状态目录、启动清单以及 MC 原生适配器的观测仍属于可信边界。同 Windows 用户权限下的任意恶意原生代码依然可能读文件、盗取租约或结束控制器；这不是 OS 沙箱、反作弊或任意恶意 JVM 控制下的无损热接管。MC 窗口重启需要重新加载，不是零停顿切换。要抵抗能任意操作宿主 OS 的攻击，需要单独账户/ACL、沙箱或虚拟机等额外隔离。此处没有修改或集成 Kimi3 的 mc-guardian。

## 验证

```powershell
.\gradlew.bat managedRuntimeTest --no-daemon --no-watch-fs
.\start-managed.ps1 -Jdk 'C:\path\to\jdk-17' -Verify
```

前者运行真实 Java 子进程，检查独立求值、超时/退出替换、旧回复拒绝、撤销和封印持久化、非法输入和损坏状态拒绝。后者另启动真正的 MC：实体被移除 → 本地模型恢复 → 玩家撤销来源 → 两个工作 JVM 换进程 → MC 整体换进程 → 恢复后拒绝外来者旧检查点 → 实际出口打开 → 再次强制结束 MC 后仍恢复已打开的出口。结果和逐阶段证据只写在本机指定目录；进程退出码本身不算通过。
