# 0.5.1：有限代际 JVM 引擎生成

本组件把 0.4 的“重新启动同一工作程序”扩展为“当前代引擎生成后继可执行类，再在新的工作 JVM 中验证和接续”。它接入 **MC Java 1.20.1 的托管和 Windows 受保护入口**。普通 Fabric 单 JVM 研究场、26.3 旁支及浏览器版没有自动获得此能力。

这里的引擎是承载 EFF 确定性规则的 Java 对象与生成类。**JDK、HotSpot 虚拟机和规则核没有被重新生成。** 新类拥有不同的类名、身份、父代和字节码摘要，但继续使用封存的同一套规则。当前生成的字节码是嵌入代际描述的构造器；规则执行和后继生成方法继承自封存基类。这提供代际隔离、可核验交接和故障恢复，不声称能消除共同规则或 JVM 漏洞。

## 此前实现与本轮变化

| 版本 | 实际实现 |
| --- | --- |
| 本地网页的 `VirtualEngine.replace` | 检查点重放及新的 JavaScript 运行对象。 |
| MC 0.3 | 判定、执行、宿主是不同 JVM；更换 PID、会话和租约。 |
| MC 0.4 | 外层守护保护代码与认证账本，清理并恢复整个受管进程树。 |
| MC 0.5 | 生成新的 JVM 可执行引擎类；后继保留相同的受限生成接口，能继续生成下一代；谱系与战局一起提交。 |
| MC 0.5.1 | 保留生成与认证交接，降低托管堆、线程、图形与引导地形的开销。 |

## 组件与执行流程

```text
封存的 EngineFactory / EngineLayer / Kernel
  → G0 引擎（判定或执行）
     → generateEngine：生成 G1 字节码包
        → 另一工作 JVM 按固定模板独立复核
           → 候选 JVM 定义新类并校验当前战局快照
              → 外层账本提交战局 + 父子谱系
                 → 撤销旧工作进程资格、结束旧进程
                    → G1 接续，且仍能生成 G2
```

1. 控制器从封存的工作 JAR 计算 `ruleset` 摘要，为判定、执行分别建立 G0 描述。
2. 当前引擎的 `generateEngine` 通过固定工厂生成自己的下一代。模板只接受角色、规则摘要、父代、代次和派生身份；不接受玩家或模型生成的 Java、class 文件、文件路径或进程命令。
3. 另一 JVM 根据预期父代重新构造后继描述与固定字节码，检查生成包。控制器也检查父子关系、代次、身份和字节码摘要。
4. 候选工作 JVM 按同一固定模板验证生成包，在新的 `ClassLoader` 中定义 `eff.generated.E<id>`。候选引擎对当前战局的快照必须与已验证结果相同，才有交接资格。
5. 战局与新谱系先提交，再切换工作进程。旧进程的回复受到原有 PID、epoch 和请求身份约束，不能回写新代状态。提交或校验失败时，不把未确认候选认作当前代。
6. 新代引擎继续通过同一接口生成后继，因此可形成 G0 → G1 → G2 的实际类生成链。每次只保留当前工作代及交接中候选，不保留不断增长的后台进程树。

若工作引擎已经退出或没有进展，它无法继续充当生成者。健康的同伴 JVM 可以依据已提交谱系，用固定工厂生成后继。故障恢复仍需复核、提交和代际预算，不重新授予外来者的游戏权限。

## 实现文件与协议

- `src/runtime/java/eff/runtime/EngineFactory.java`：描述校验、固定字节码模板、摘要与受限类加载。
- `src/runtime/java/eff/runtime/EngineLayer.java`：生成类的基类，承载规则入口与受限后继生成能力。
- `src/runtime/java/eff/runtime/Worker.java`：工作 JVM 的管道协议与一次启动握手。
- `runtime/engine-lineage.cjs`：控制器侧的描述、谱系及生成包检查。
- `runtime/controller.cjs`：候选验证、提交、资格切换、进程清理和故障预算。
- `runtime/guard/WindowsGuard.cs`：受保护模式中的谱系追加约束与认证账本。

每个描述包含以下字段：

```text
schema: 1
role: policy | execution
generation: 0..16
parent: GENESIS | 上一代引擎 id
ruleset: 封存工作 JAR 的 SHA-256
id: SHA-256("eff-engine-v1\n" + role + "\n" + ruleset
           + "\n" + generation + "\n" + parent)
```

生成包包含 `descriptor`、Base64 `artifact`、`bytecodeSHA256` 和 `className`。启动证明的结构为 `{descriptor, bytecodeSHA256, className, loaderId}`，也通过 `snapshot.runtime.policy.engine` 和 `snapshot.runtime.execution.engine` 返回。代次、父代和身份位于嵌套的 `engine.descriptor` 中。`loaderId` 对应实际定义加载器。`loaderId` 是本次进程内的诊断身份，不代替代码摘要或谱系认证。

| 工作协议操作 | 输入和行为 |
| --- | --- |
| `prepareEngine` | 输入 `descriptor`，用可信模板重建生成包；也用于已提交代的恢复。 |
| `bootEngine` | 输入 `packet`，重新校验固定字节码，定义并启动引擎；每个工作进程只能成功启动一次。 |
| `generateEngine` | 已启动引擎生成自己的直接后继包。 |
| `verifyEngine` | 输入 `parent` 和 `packet`，独立复核父子关系及固定字节码。 |
| `initial` / `snapshot` / `transition` | 启动后由当前生成类承载；没有完成启动握手时拒绝执行。 |

这些操作走控制器持有的标准输入/输出管道，未作为玩家 HTTP 接口或模型工具开放。引擎不会把任意传来的字节码直接交给类加载器；先按可信工厂重建并比较完整字节码。

## 与代码保护和存档的配合

生成类只存在于工作 JVM 内存中，不写入可执行 JAR、可写配置或封存的 `payload`。因此不需要放宽静态目录成员检查，也不会在每次生成时重建信任清单。固定工厂、基类和规则核仍由 0.4 的代码锁与哈希校验保护。

`body.engines.policy` 与 `body.engines.execution` 保存从 G0 到当前代的描述链。它们和 `state` 一起进入外层认证账本。新提交只能保持原链或追加一个直接后继，不能删链、改写已提交祖先、跳代或更换规则摘要。受保护模式由外层独立检查这些约束；开发托管模式没有外层密钥保护。

控制器恢复时重建账本中最后接受的引擎类，保留原谱系，不回到 G0。重建同一已提交代是基础设施恢复，不计作新一次生成；后续显式换代仍从该代继续。原有 `state.generation` 是地图实例代次，与引擎 `generation` 分开。

已有的授权撤销、检查点封印、触发器记录、轮次和结局仍属于同一已提交战局。生成新引擎不能使 `authority.recovery` 从 false 回到 true，也不能给外来者重新启用旧检查点。

## 如何游玩和查看结果

按 [受保护启动说明](./PROTECTED_RUNTIME.md)从新代码准备一个**新目录**。旧的 0.4 或 0.5.0 封存目录不会自动更新代码。不要对旧目录重新采样清单，也不要覆盖它的账本。

进入运行层研究场后，仍使用原有受限程序：

```text
rebuild runtime.execution
rebuild runtime.policy
```

它们现在分别生成并激活执行、判定后继。界面展示实际工作 JVM 的 PID、引擎 G 代次、身份短摘要和字节码短摘要。完整身份、父代、类名及换代事件包含在控制器回执中，供本地诊断；画面撕裂本身不算换代证明。

```text
rebuild runtime.host
```

此指令仍会真正结束并重新加载 MC 宿主窗口，使用已提交战局恢复研究场。它不会生成新的 Minecraft 二进制、渲染引擎或 JVM 实现。世界对象的 `rebuild instance.world` 也继续保留原有含义。

外来者只能在已有权限和候选集合允许时提出运行层干预。`authority.recovery` 被撤销后，不能借新代引擎绕过撤销。模型输出仍是受限程序建议，最终状态由确定性执行与独立判定共同确认。

## 低内存运行

0.5.1 的托管与受保护入口默认设置 `eff.lowMemory=true`。MC 使用 768 MiB Java 堆、128 MiB 直接缓冲上限、SerialGC、64 MiB code cache 和两核；工作 JVM 各为 64 MiB 堆、24 MiB code cache 和两核。控制器与低内存剧情桥各限定 96 MiB V8 堆。准备阶段的 JAR 工具使用 64 MiB 堆，大文件哈希使用 1 MiB 分块缓冲。

专用研究场通过平坦引导世界加载，再进入原生 `eff:phenomenon` 战场，避免每次控制器恢复都重新生成普通地形。托管视距为 2、模拟距离为 5；截图纹理在演出结束、跳过和客户端退出后释放。普通安装及用户自有世界不套用这些预览设置。低内存模式不自动加载模型；需要本地推理时由玩家手动启用并预留模型内存。

这些配置减少常驻与准备阶段峰值，不改变候选代独立验证、先提交后交接、认证谱系或旧进程清理。候选 JVM 在交接期间仍会短暂增加占用；堆上限不等于进程总内存。开发者可在 Gradle 导出时使用 `-PeffLowMemory=false`，恢复 2 GiB MC 堆和普通引导世界，再封存到新目录。

## 有界性、失败与验证

每个角色允许 G0 至 G16，达到上限后拒绝继续生成。原有超时、工作进程熔断、守护重启预算、Job Object 进程数与内存上限继续适用。没有无限自复制、后台安装或自动下载代码的路径。换代会耗时，MC 宿主重启需要重新加载，不能当作零停顿热迁移。

本组件应验证以下行为，实际通过结果以本轮构建输出及本机原生回执为准：

- 连续多代产生不同类身份与字节码摘要，新代可再次生成下一代并执行规则。
- 错误父代、身份、字节码、跳代、谱系回退及超预算会被拒绝；未经启动握手不能执行语义。
- 候选校验或账本提交失败时不激活，权限撤销和终局保持不变。
- 工作进程失败能由健康同伴生成后继；没有无限新建进程。
- 控制器被结束后，外层账本保留谱系与战果；守护被结束仍清理整个受管子树。
- MC 中通过现有换代指令触发真实生成与切换，之后仍能完成夺权并实际打开出口。

构建与控制器检查使用 `gradlew.bat build --no-daemon --no-watch-fs`。受保护原生检查使用 `start-protected.ps1 -Verify -Jdk <Java17路径>`。原生验收使用同样的低内存配置和专用世界。阶段时限从原生研究场就绪后计时，另保留 180 秒的宿主加载预算和每段 240 秒的验收等待上限。构建通过不能代替真实 MC 回执，也不能推出任意第三方模组或同权限恶意程序均被隔离。

若本机无法加载模型，可显式使用 `start-protected.ps1 -Verify -AllowRuleFallback -Jdk <Java17路径>`，只验收真实 MC、规则反制、生成与恢复。默认原生验收仍要求本地模型恢复；允许回退的回执会记录 `counterSource` 和 `modelInferenceVerified:false`，不能当作模型推理通过。

信任边界仍包括最初的源码与准备步骤、固定工厂和规则核、JDK、Windows 账户、外层守护以及 MC 原生观测。生成类遵循同一套算法，独立进程复核不能证明共享规则没有错误。该组件不提供针对任意管理员操作、内存注入或宿主操作系统攻击的免疫。
