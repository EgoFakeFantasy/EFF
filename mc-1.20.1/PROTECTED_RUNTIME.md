# 受保护多 JVM 运行时（Windows，0.5.1）

推荐通过 `Start-Protected.cmd` 或 `start-protected.ps1` 启动。0.5 的[有限代际引擎生成](./RECURSIVE_ENGINES.md)在此保护链内运行；后继类只在工作 JVM 内存中生成，静态封存清单不重新采样。普通 Fabric 模组入口仍然是单 JVM；旧的 `start-managed.ps1` 是开发托管入口，没有本页的外层代码和日志保护。

## 信任链和实现

```text
首次可信准备 → 启动器固定守护 EXE / CLR 配置哈希，并持有只读共享句柄
  → WindowsGuard：固定清单哈希 + 核心代码只读句柄 + 认证提交日志
     → Job Object（关闭守护或结束旧控制器时清理整个受管子树）
        → Node 控制器（可整体替换，通过私有管道请求提交）
           ├─ 判定 JVM
           ├─ 执行 JVM
           └─ MC JVM → 已封存的 Node 剧情桥 → 本机 Ollama 服务
```

外层守护由本机 .NET Framework 编译器构建，不安装服务、计划任务或新的 JDK/模型。Job Object 没有脱离标志，限制为 16 个受管进程、8 GiB 作业内存。已有 Ollama 服务不在进程树内，不会被关闭。Node 控制器另限制 V8 堆，工作 JVM 仍有限额。0.5.1 默认的低内存配置如下。

### 默认内存配置

| 组件 | 低内存配置 |
| --- | --- |
| MC 宿主 | 768 MiB Java 堆、128 MiB 直接缓冲上限、SerialGC、64 MiB code cache、两核。 |
| 判定与执行 JVM | 每个 64 MiB Java 堆、24 MiB code cache、两核；交接时还会短暂存在候选 JVM。 |
| Node 控制器 | 96 MiB V8 堆上限。 |
| Node 剧情桥 | `eff.lowMemory` 下为 96 MiB V8 堆上限。 |
| 准备阶段 JAR 工具 | 64 MiB Java 堆；大文件哈希使用 1 MiB 分块缓冲。 |

这些是堆和指定缓冲的上限，不是整棵进程树的总内存承诺。Java 原生内存、线程、图形驱动和可选模型仍需额外空间；8 GiB Job 上限用于限制总量，不代表启动就会占用这么多内存。

低内存托管研究场使用专用平坦引导世界，实际战场仍在原生 `eff:phenomenon` 维度；视距为 2、模拟距离为 5。演出截图在结束、跳过和退出后退役释放。低内存入口不自动加载本地模型，玩家可手动启用已有模型。

开发者可在 Gradle 导出启动清单时使用 `-PeffLowMemory=false`，恢复 2 GiB MC 堆和普通引导世界。启动配置变更仍需准备一个新目录；不重新封存已有运行目录。

### 代码保护

- 受保护目录只允许显式准备一次；启动不会重建清单、重新采样信任或覆盖已有战局。代码更新需要从可信源码准备一个新目录。
- 启动器先锁定并核验守护 EXE 和 `.exe.config`，再启动守护；守护按启动器固定的 SHA-256 核验清单，锁定其中每个文件并检查内容及大小。缺文件、哈希不符或重解析点均拒绝启动。
- `FileShare.Read` 允许正常加载，但禁止其他打开者取得写入或删除共享权限。运行期间，覆盖、删除和重命名已保护文件都被 Windows 拒绝。它不只是周期性重新计算哈希。
- 清单覆盖控制器、辅助模块、完整工作进程 JAR、Node EXE、相关 JDK 的 bin/lib/conf，以及 MC 显式 classpath JAR 和启动配置。开发用的 classes/resources 目录先合成为私有 JAR，显式依赖 JAR 和 remap classpath 也复制并重定向到私有目录；游戏不从持续变化的编译目录或临时 Gradle JAR 缓存加载代码。
- 剧情桥先从可信构建包解出并封存。MC 通过固定路径读取它，不会在可写配置目录重新生成和运行脚本。
- 新增辅助文件、额外模组或目录成员变化会被检查并导致停机；这项检查是变化检测，不能替代操作系统对任意恶意原生代码的隔离。
- 不把游戏或模型产生的文本作为启动命令。准备时拒绝额外 agent/启动代码注入参数；子进程环境清除 JVM/Node 参数注入项，工作 JVM 和剧情桥不继承 MC 的控制通道租约。

### 提交日志保护

`WindowsGuard` 独占持有 `ledger.bin` 和 `ledger-head.bin` 的写句柄，保持只读共享；Node 控制器、MC 和两个工作 JVM 都不能直接改写它们。控制器只通过自己的标准输入/输出私有管道请求 load、verify、commit；游戏的 HTTP 通道不能调用这些接口。

每条提交含单调版本、上一条认证值和 HMAC-SHA256。独立头记录保存最后提交位置；在线控制器替换期间，守护内存也保留当前版本。把日志截成旧的、签名仍合法的前缀会被拒绝。密钥在首次准备时生成，落盘用当前 Windows 用户的 DPAPI 保护，运行时只在守护内存中使用，不进入 MC、模型进程或控制器的环境变量。

外层还独立拒绝恢复已撤销的授权、倒退状态版本以及改写已提交的终局。记录缺失、认证失败、头记录缺失或落盘状态不确定时停止运行，不初始化成新的战局。日志追加和头记录写入后均请求同步落盘；控制器只在外层确认后承认提交。

这不是任意离线回滚的绝对证明：如果攻击者能在所有守护停止后，把日志、密钥和独立头记录一起恢复成一整套旧的有效副本，单靠这些文件无法识别。更强保证需要独立身份、外部可信存储或硬件单调锚点。

### 控制器恢复和通信

- Node 控制器死亡或事件循环长期无进展时，外层先终止旧 Job 并确认活动进程数为零，再启动新控制器。旧 MC、工作 JVM 和剧情桥不会作为孤儿继续运行。
- 新控制器从仍由外层持有的最后提交接续；新 MC 使用新会话、新租约和新世界目录。旧进程的回写没有资格。
- 外层自己被结束时，内核关闭 Job 句柄并结束其正常创建的受管子进程。不采用无限互相拉起；短时重启和总恢复次数都有预算。
- 请求和响应都使用 HMAC 认证，区分请求/响应域；网络上传输认证值而不是直接传输租约密钥。心跳有单调序号，重复请求有去重记录；写操作另受战局版本约束。
- 心跳必须来自有效会话，客户端/服务端循环计数不能倒退。过期或重放数据不会刷新健康时间。超时、退避和重启窗口使用单调时间；墙钟只用于日志。
- 应用层继续区分世界加载、原版暂停与模拟冻结；宿主加载预算为 180 秒，原生验收每段等待有 240 秒总预算；操作阶段时限从研究场原生状态就绪后开始。HTTP 请求有大小、并发、头部和读取时限，工作进程消息与对局回执也有总量限制。

## 准备、启动和更新

需要 Windows 10/11、.NET Framework 4.8、Java 17 JDK 和 Node.js 22+。首次 Fabric/Gradle 依赖准备需要网络。守护源码位于 `runtime/guard/WindowsGuard.cs`，构建不下载第三方守护二进制。

```powershell
# 从已核实的源码准备一个新的目录；只准备，不自动开始游戏
.\start-protected.ps1 -Prepare -Jdk 'C:\path\to\jdk-17' -Directory 'C:\path\to\eff-protected'

# 后续启动只校验和运行，不重新构建/封存
.\start-protected.ps1 -Directory 'C:\path\to\eff-protected'
# 也可以直接双击该目录的 Start-Protected.cmd
```

目录中 `payload` 是代码，`authority` 是私有战果和密钥，`mc-host` 是专用研究场。不要把它当作普通 MC 存档启动器。停止游戏或 Ctrl+C 会停止受管树；没有注册后台自启动项目。换 JDK/Node 或更新代码后，应重新准备一个新目录，保留旧目录供核对；此入口没有自动迁移旧版 SHA 校验存档的功能。

初次准备和启动器本身属于可信根。不要从已经可疑的源码运行准备步骤，把投毒代码重新认定可信。私有清单、密钥、状态、日志和本机启动脚本不要提交 Git 或打进公开包。

## 本轮验证

```powershell
.\gradlew.bat build --no-daemon --no-watch-fs
.\start-protected.ps1 -Verify -Jdk 'C:\path\to\jdk-17'
```

Windows 构建包含原生守护检查：实际禁止写入/删除/替换代码及日志；双守护争写拒绝；控制器终止后清空 Job 并保留撤销；结束外层后子树退出；旧日志前缀、缺失头记录、篡改代码、清单与 CLR 配置被拒绝。控制器检查另覆盖 HMAC 消息篡改/重放、心跳重放和墙钟回拨。

真实 MC 验证流程为：本地模型恢复实际投影（显式 `-AllowRuleFallback` 时使用规则反制） → 玩家撤销来源 → 连续生成并验证后继引擎 → 强制结束整个控制器 → 旧 Job 清空 → 新控制器和 MC 从外层日志恢复 → 权限仍撤销并实际打开胜利出口 → 再结束外层守护，确认所有受管进程退出。结果只写本机 `native-result.json`，游戏或守护退出码本身不算通过。允许规则回退时会记录实际反制来源，不能当作本地模型推理已通过。

## 与本机 mc-guardian v5 的比较

本轮只读取、复制到隔离测试目录编译和核验所提供的源码，没有修改其目录，也没有运行安装计划任务或伙伴复活流程。

值得吸收的是 HMAC 与序号、固定复活目标、白名单、单调时间、退避和熔断。隔离探针也发现：当前实现中空白名单可以放行已改动文件；心跳令牌在整个监督周期生成一次，验证器保留旧序号，新子进程从 1 计数时会被拒绝。因此本版实现独立的封存、每次宿主轮换身份、外层持有日志和内核进程树清理，没有直接拼接该组件或它的存档副本方案。探针不是其所有功能的完整安全审计。

同 Windows 用户权限下，能任意操纵操作系统、守护内存或启动器的攻击者，仍可突破这一可信边界。DPAPI 不隔离同一用户的任意恶意程序，Job Object 也不是安全沙箱。这个版本加强的是代码文件的运行期写保护、可观察故障后的恢复和提交连续性，不承诺无缝接管任意 MC 内存或对所有运行层攻击免疫。

实现依据：[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[文件共享与打开语义](https://learn.microsoft.com/en-us/windows/win32/fileio/creating-and-opening-files)。
