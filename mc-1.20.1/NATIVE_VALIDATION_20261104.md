## 干净 MC 基线暴露的问题

1. 首次在普通权限下设置 MIC 标签失败，错误 `INTEGRITY_LABEL_FAILED_5`。父目录仅继承 Modify，没有设置标签所需的 WRITE_OWNER。修复只针对新建、空、当前用户拥有且非 reparse 的部署目录，先用 owner 的 WRITE_DAC 设置用户／SYSTEM DACL；原来的 NR/NW/NX 标签不减弱。
2. 修复后 Forge 启动参数仍使用打包时的占位 `--gameDir`，不存在而导致退出。封存器现在将其统一到该部署的 `mc-host`，拒绝重复、缩写和隐藏的游戏／模组目录覆盖。纯策略测试通过；实际 MC 重跑仍待完成。
3. 后续干净 Windows 在未加载 MC／样本时多次无响应，涉及 headless／GUI、3D 开启／关闭。日志显示 NEM/WHPX 执行路径及 GuestControl 超时，但这些现象尚不能单独确认根因。单核诊断一度完成编译和原生测试，随后也发生无响应；最新完整日志通过只取证的恢复启动取回，结果 JSON 为全 NUL，不能用于验收。虚拟机最终已关机。没有通过关闭 Hyper-V、VBS、杀毒软件或添加排除项继续测试。

## 工程边界

保护重点是权限域、进程对象和目录的访问控制、可信启动输入、外部权威状态与有限恢复；C／Rust 本身不会授予更高权限。同 JVM 中任意原生代码仍可破坏自身内存或退出 JVM。用户态监督器不能超过其依赖的 Windows 内核；需要更强边界时必须把最终权威放到独立宿主／虚拟化边界或其他机器。

Rust 当前换代重新启动同一固定可信二进制，重置子监督器上下文和受控运行树，不是每代编译新的 Rust 机器码。固定 root 的安全替换需要更外部验证者，尚未实现。启动后自标记也不能撤销此前取得的句柄，完整消除这段创建竞态需要可信创建者在创建进程时给定安全描述符。见 [工程蓝图](RUST_SUPERVISOR_BLUEPRINT.md)。
